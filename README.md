Task Service with Periodic Tasks

## TL;DR

В проект добавлена поддержка периодических задач.

Ключевые идеи решения:

- хранится **одна задача**, а не множество записей;
- периодичность задаётся через `recurrence_type` и `recurrence_config`;
- следующая дата вычисляется **в момент завершения задачи**.

Поддерживаемые типы периодичности:

- `daily_every_n`
- `monthly_day`
- `specific_dates`
- `even_days`
- `odd_days`

---

## Описание

Сервис представляет собой API для управления задачами.

Поддерживаются следующие операции:

- создание задачи;
- редактирование задачи;
- удаление задачи;
- просмотр одной задачи и списка задач;
- завершение задачи.

Дополнительно реализована поддержка **периодических задач**, позволяющая описывать правила повторения и пересчитывать следующую дату выполнения.

## Модель задачи

```go
type Task struct {
    ID               int64
    Title            string
    Description      string
    Status           string
    ScheduledAt      time.Time
    RecurrenceType   string
    RecurrenceConfig json.RawMessage
    CreatedAt        time.Time
    UpdatedAt        time.Time
}
```

### Поле `scheduled_at`

- хранит следующую дату выполнения;
- **не может быть `NULL`**;
- обновляется при каждом `complete`.

Если точная дата заранее неизвестна, допускается использовать техническое значение.

## Типы периодичности

| Тип | Описание | Пример `recurrence_config` |
| --- | --- | --- |
| `none` | без повторения | `{}` |
| `daily_every_n` | каждые N дней | `{ "every": 2 }` |
| `monthly_day` | определённый день месяца | `{ "day": 15 }` |
| `specific_dates` | список фиксированных дат | `{ "dates": [...] }` |
| `even_days` | только чётные дни месяца | `{}` |
| `odd_days` | только нечётные дни месяца | `{}` |

## Поведение периодических задач

### Основная идея

Система **не создаёт заранее отдельные задачи для будущих повторений**.

Вместо этого используется следующий подход:

- в базе хранится **одна запись задачи**;
- в этой записи хранится правило повторения;
- следующая дата вычисляется **в момент завершения задачи**.

Преимущества такого подхода:

- меньше данных в базе;
- проще изменять правило периодичности;
- не требуются фоновые процессы для генерации будущих задач.

---

### Алгоритм работы

При вызове `POST /tasks/{id}/complete` выполняется следующая логика:

1. Проверяется тип периодичности задачи.
2. Если `recurrence_type = none`, задача помечается как `done`.
3. Если задано правило повторения:
  - создаётся соответствующая реализация `Rule`;
  - вызывается метод `Next(scheduled_at)`.
4. Далее результат обрабатывается так:
  - если следующая дата **найдена**, поле `scheduled_at` обновляется, а статус задачи переводится в `new`;
  - если следующей даты **нет** (это возможно для `specific_dates`), задача помечается как `done`.

Сигнатура расчёта следующей даты:

```go
Next(scheduled_at)
```

---

### Как вычисляется следующая дата

Логика зависит от типа правила:

- **`daily_every_n`** — к текущему `scheduled_at` прибавляется `N` дней;
- **`monthly_day`** — ищется ближайшая будущая дата с указанным днём месяца;
- **`specific_dates`**:
  - список дат сортируется;
  - выбирается первая дата, строго большая текущей;
  - если подходящих дат нет, серия завершается;
- **`even_days` / `odd_days`** — дата увеличивается на 1 день, пока не выполнится условие на чётность дня месяца.

Все операции выполняются в **UTC**.

---

### Важный нюанс: от чего считается следующая дата

Следующая дата всегда вычисляется **от текущего `scheduled_at`, а не от текущего времени**.

Пример:

- `scheduled_at = 1 апреля`
- правило: каждые 2 дня
- задачу закрыли 20 апреля

Результат:

```text
Next(1 апреля) = 3 апреля
```

То есть новая дата может оказаться в прошлом.

Это сделано намеренно, потому что такой вариант:

- упрощает реализацию;
- делает поведение предсказуемым;
- сохраняет логику движения строго по расписанию.

### Пример сценария

Создание задачи:

```http
POST /api/v1/tasks
Content-Type: application/json

{
  "title": "Call patients",
  "scheduled_at": "2026-04-20T10:00:00Z",
  "recurrence_type": "daily_every_n",
  "recurrence_config": {
    "every": 2
  }
}
```

Завершение задачи:

```http
POST /api/v1/tasks/{id}/complete
```

Результат:

```json
{
  "status": "new",
  "scheduled_at": "2026-04-22T10:00:00Z"
}
```

## Осознанные ограничения

В рамках задания приняты следующие упрощения:

- **Расчёт от `scheduled_at`**
  - текущее время не учитывается;
  - после завершения возможна новая дата в прошлом.
- **Нет catch-up механизма**
  - система не догоняет пропущенные даты автоматически.
- **Нет ограничения количества повторений**
  - все правила, кроме `specific_dates`, потенциально бесконечны.
- **Ограничение `monthly_day` до 1–30**
  - это исключает неоднозначности, связанные с длиной месяцев.
- **UTC only**
  - все даты хранятся и сравниваются в UTC.

## Архитектура

Используется подход:

```text
recurrence_type + recurrence_config + Rule interface
```

### Почему выбран именно этот вариант

- нет большого количества nullable-полей;
- валидация остаётся простой и понятной;
- решение хорошо расширяется новыми типами правил;
- данные и поведение разделены явно.

Каждое правило реализует единый интерфейс:

```go
type Rule interface {
    Validate() error
    Next(time.Time) (time.Time, error)
}
```

По сути это реализация **Strategy Pattern**, где каждое правило инкапсулирует собственную логику расчёта.

## Альтернативы

### Генерация задач заранее

Минусы:

- большое количество записей в базе;
- сложная синхронизация при изменении правил;
- потребность в фоновых процессах.

### Единая структура с множеством полей

Минусы:

- много nullable-полей;
- сложная валидация;
- высокий риск некорректных комбинаций.

### Использование cron-выражений

(когда расписание описывается одной строкой в формате cron, например запуск по дням недели, часам и минутам)

Минусы:

- избыточность для данной задачи;
- усложнение парсинга и валидации;
- ухудшение читаемости API.

### Отказ от хранения `scheduled_at`

(когда в задаче хранится только правило периодичности, а ближайшая дата не сохраняется отдельно в базе)

Минусы:

- неэффективные SQL-запросы;
- необходимость пересчитывать дату при каждом чтении;
- ухудшение производительности.
